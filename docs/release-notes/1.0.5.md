# apt-cacher-ultra 1.0.5

Fix background snapshot adoption failing against the Raspberry Pi archive with
`member_fetch_failed main/source/Sources served 123988 vs declared 443932`
([issue #32](https://github.com/linsomniac/apt-cacher-ultra/issues/32)). Thanks
to @hraphael for reporting the problem and clarifying the affected configuration.

The archive returns `Sources.gz` bytes when ACU requests the uncompressed
`Sources` URL. This can affect the default adoption configuration even when
clients do not use `deb-src`, and APT operations can continue while the admin
status reports degraded adoption.

ACU now explicitly fetches or reuses a gzip/xz sibling declared by the same
Release, verifies its size and SHA-256 hash, decompresses it, and verifies the
plain index against its own declaration. The same recovery covers Packages,
reconciliation, and missing cached snapshot indexes. Recovery uses only the
selected snapshot's content and keeps bounded downloads and decompression;
response headers alone never establish a file's identity.

This is a backport to the 1.0.x release line. It retains 1.0.x's SHA-256 Release
verification and existing adoption policy. No configuration change, database
migration, cache deletion, or upgrade to 1.1.0 is required.

Upgrade and restart normally. Recovery takes effect on the next adoption or
applicable reconciliation/cache recovery. An `index_reconstructed` INFO event
records recovery; a subsequent successful adoption confirms the suite was
published. See the [configuration reference](https://github.com/linsomniac/apt-cacher-ultra/blob/1.0.5/docs/configuration.md#architecture-and-member-availability)
and [log reference](https://github.com/linsomniac/apt-cacher-ultra/blob/1.0.5/docs/log-fields.md#index-reconstruction-105).

The regression suite includes the actual Raspberry Pi archive bytes: the direct
fetch reproduces the reported 123,988/443,932-byte mismatch, then adoption with
the default architecture filter publishes both correct representations.
