# apt-cacher-ultra 1.1.0-rc3

**This is an opt-in release candidate for testing the upcoming 1.1 release.
The recommended stable release remains 1.0.5.** Download the candidate's
binary or `.deb` from the release assets; the stable apt repository continues
to serve stable releases only.

RC3 changes how a new release's package list is written to the database, so
that publishing an update no longer holds every other database write for
seconds, and fixes two faults found in a production cache's logs. It includes
everything in RC2 and the earlier 1.1 work on flat repositories, snapshot
consistency, signature verification, garbage collection, HTTPS/ACME,
readiness and usage statistics.

## Changes since RC2

- **An update's commit writes what changed.** Each suite now has one package
  list, updated in place, instead of a copy per snapshot, and the switch to
  a new release writes only the rows the publication changed. Every write in
  the daemon runs through one database writer, so the old whole-list commit
  held up client cache misses, other suites' switches and garbage
  collection. On a production cache the commit of its largest suite (66,000
  packages) took 12 to 24 seconds before the change, over 31 adoptions in
  six days, and 0.6 seconds after; 86 commits held the writer five seconds
  or longer in those six days, and none in the first ten hours after. A
  suite's first adoption, and a publication that changes more than half of
  its packages, still write the whole list.
  `adoption.write_package_list_differences = false` makes every adoption
  write the whole list again: a fallback, not a tuning knob. See
  [the measurements](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0-rc3/docs/superpowers/specs/2026-11-18-package-list-per-suite-design.md#on-a-production-cache-2026-11-21).
- **Reading a `Packages.xz` no longer costs a system call per byte.** The xz
  decoder read the cached index one byte at a time: 1.47 million reads for a
  1.47 MB file. On that production cache this was most of an adoption, 38 to
  40 seconds of the 55 to 78 a large suite took. On a development machine
  the same file now decodes in 0.20 seconds where it took 0.72; the gain on
  a production host is not measured yet.
- **Plain files served as their compressed sibling are treated as not
  published.** packages.icinga.com lists `Contents-amd64` and
  `Contents-amd64.gz`, publishes the `.gz` only, and answers a request for
  the plain name with the `.gz` and status 200 (Apache content negotiation).
  apt never asks for the plain name. ACU did, took the answer for a failure
  that might heal, waited two retry rounds at every publication, and fetched
  the file again at every unchanged check without end; with
  `tolerate_optional_member_failures = false` the suite did not adopt. When
  the answer is exactly the sibling the same `Release` declares, the plain
  file is now skipped like one answered 404
  (`adoption_member_skipped`, `reason=compressed_sibling_served`), and the
  record an earlier version left for the repair pass is dropped at its next
  run. `Packages` and `Sources` served this way are still rebuilt from the
  sibling (#32).
- **Empty components on Cloudsmith.** A zero-byte `Packages.gz` is accepted
  when a zero-byte `Packages` in the same directory of the same release
  verifies, so the Caddy repository adopts.
- **Logs say what a database write waited behind.** `adoption_finished` and
  `background_work_finished` carry `writer_wait_seconds` and `writer_ahead`,
  and the INFO event `database_write_waited` reports any write, a client
  request's included, that waited two seconds or more. See
  [waiting for the database writer](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0-rc3/docs/log-fields.md#waiting-for-the-database-writer).

## Before upgrading

Read the [full upgrade notes](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0-rc3/docs/release-notes/1.1.0.md#before-you-upgrade).
In particular:

- Stop the daemon and back up the cache, any separate database directory
  (including its WAL), and configuration before testing. A disposable copy of
  an existing cache is preferable for the first upgrade.
- **RC3 migrates to schema 11. RC2 uses schema 10, RC1 schema 9, and 1.0.x
  schema 6.** No older binary can open the migrated database. Returning to
  RC2, RC1 or 1.0.x requires restoring the pre-upgrade backup; reinstalling
  the older binary alone is insufficient. The migration drops the package
  lists earlier versions kept for displaced snapshots.
- **Be patient with the first start.** The migration runs before the ports
  open: 5 to 10 seconds for a database of 1.16 million package rows on a
  development machine, and 68 seconds on a production host with suites of
  the same size. Do not restart the daemon to hurry it; an interrupted
  migration starts again from the beginning. Installing the `.deb` restarts
  a running daemon, and startup auditing and background cleanup can take
  time on a large cache.
- **The migration needs free disk.** For 290,000 current package rows the
  write-ahead log beside the database grew to 170 MiB, the database file by
  79 MiB (by nothing when it already has free pages), and SQLite sorted
  45 MiB in its temporary directory. Allow
  about 1.3 KiB per current package row. The daemon does not check for the
  space beforehand: on a disk too full the migration fails, the daemon
  exits, and the next start begins it again.
- Offline/archive caches should set `gc.suite_idle_ttl = "0s"` before
  upgrading if idle suites must be retained. The suite reaper runs even with
  `gc.enabled = false`.
- Snapshot adoption remains opt-in. Load repository signing keys before
  enabling it. Restarting with adoption disabled forgets previously adopted
  suites so their metadata can refresh through the ordinary cache.
- Existing explicit configuration values are retained. A cache that still
  sets `freshness.periodic_refresh = "15m"` or a long
  `adoption.hot_prefetch_budget` keeps them (the daemon warns at start,
  `publication_latency_settings`); edit them to receive RC2's shorter
  delays.

## Dashboards and alerts

- `adoption_finished` says how the commit wrote the package list:
  `package_list_write` (`difference`, `rewrite` or `none`),
  `package_rows_added`, `package_rows_changed`, `package_rows_removed`, and
  for a rewrite `package_list_rewrite_reason`.
  `acu_adoption_package_list_writes_total{mode,reason,host}` counts them.
- Two new events mean the difference path fell back to writing the whole
  list: WARN `package_list_diff_failed` (the stored list could not be read
  beforehand) and ERROR `package_list_mismatch` (a difference did not
  produce the publication's rows: a defect, please report it). The snapshot
  published is correct in both cases.
- GC's counter of deleted package rows was
  `acu_gc_displaced_package_rows_deleted_total` in the earlier candidates
  and is now
  `acu_gc_package_list_rows_deleted_total`; the field
  `displaced_package_rows_deleted` of `gc_run_complete` and
  `gc_retired_run_complete` is now `package_list_rows_deleted`.
- `adoption_member_skipped` has the new reason `compressed_sibling_served`
  (with `served_as`), `adoption_repair_pass` a `retired` count, and
  `acu_adoption_member_repairs_total` the outcome `not_published`.

The [log field reference](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0-rc3/docs/log-fields.md)
has every event and field.

## Downloads and installation

Assets include a standalone Linux amd64 binary, a Linux amd64 `.deb`, a source
archive, and `SHA256SUMS`. After reading the upgrade notes and backing up,
download `apt-cacher-ultra_1.1.0-rc3_amd64.deb` and `SHA256SUMS` into the same
directory:

```sh
sha256sum --check --ignore-missing SHA256SUMS
sudo apt install ./apt-cacher-ultra_1.1.0-rc3_amd64.deb
apt-cacher-ultra -version
sudo systemctl start apt-cacher-ultra
sudo systemctl status apt-cacher-ultra
```

Install only if the checksum check passes. The package's internal Debian
version is `1.1.0~rc3`, which sorts after RC2 and before stable 1.1.0. The
download filename uses `-rc3` because GitHub rewrites `~` in asset names.

## Remaining limits and feedback

- The package-list change has run on one production cache for ten hours.
  Every adoption there changed no package row, or added one and removed one
  (the publications changed AppStream files or phased-update percentages),
  so a difference of
  many rows, a whole-list rewrite and the daily garbage collection have been
  exercised in tests and the freshness lab only. Please report any
  `package_list_mismatch` or `package_list_diff_failed`, and how long the
  first start's migration took on your cache.
- Please report GC behavior on busy real caches ([#14](https://github.com/linsomniac/apt-cacher-ultra/issues/14)).
- `do-release-upgrade` needs the client's system certificate store to trust
  the proxy's MITM CA, or the proxy must be bypassed for that operation
  ([#19](https://github.com/linsomniac/apt-cacher-ultra/issues/19)). Disabling
  MITM does not provide a CONNECT pass-through tunnel.
- Signature compatibility exceptions and deferred integrity cases remain in
  [open decisions](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0-rc3/docs/open-decisions.md#open).

Please report the version, relevant configuration with secrets removed, logs
and reproduction steps in [GitHub issues](https://github.com/linsomniac/apt-cacher-ultra/issues).
See the [full 1.1 release notes](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0-rc3/docs/release-notes/1.1.0.md)
for the complete feature and upgrade details.
