# apt-cacher-ultra 1.1.0

1.1.0 makes flat apt repositories — pkgs.k8s.io, NVIDIA CUDA,
libnvidia-container, pkg.jenkins.io, Sublime Text and the like — first-class:
with snapshot adoption enabled, the cache now refreshes them, adopts them as
coherent snapshots and vouches their packages for strict mode. It also
adopts unsigned and SHA512-only repositories, refreshes Release-less ones
file by file, adopts a new repository at its first `apt update`, backs off
from failing upstreams instead of retrying them at every check, keeps
clients from straddling a snapshot switch, and drops suites no client uses.

Verified snapshots and package vouching need snapshot adoption
(`[adoption] enabled = true`, after loading your repositories' signing keys),
which the packaged configuration leaves off. With adoption off, changes to a
tracked `InRelease` or `Release` now invalidate the suite's mutable metadata;
subsequent requests fetch current files. This fixes repositories remaining
frozen at their first cached release (#18). Existing adopted snapshots still
need adoption to refresh; the cache warns instead of bypassing verification.
The status page reads "ADOPTION DISABLED". See
[Repositories](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/README.md#repositories).

Responses now preserve valid upstream `Last-Modified` dates for their URL and
content instead of exposing local cache timestamps (#17). Content ETags support
304 responses. Date-only conditions receive full bodies, preventing repeated,
backward or previously synthetic dates from hiding an update. An origin date
that was never recorded, is invalid, or is in the future is omitted. The schema
8 migration retains previously stored URL and snapshot-anchor dates.

This release also adds optional HTTPS for the admin and cache listeners,
certificate file reload, and automatic ACME HTTP-01/DNS-01 issuance and renewal.
These features work independently of snapshot adoption; see
[server HTTPS and automatic certificates](#server-https-and-automatic-certificates).

With adoption enabled, the cache now checks an upstream's `InRelease` or
`Release.gpg` as strictly as the apt clients it serves: it refuses an
anchor whose format a supported apt rejects (measured on 904 signature
shapes with the apt of eleven client images, apt 1.0 to 3.2), a bad
signature from any key it holds beside a good one, and a signature hashed
with SHA-1, and a new *signer downgrade guard* refuses an anchor that has
lost the strong signer its suite's current one has. A refused anchor never
replaces what the suite serves. Garbage collection frees disk again on a
busy cache (issue #14), and an empty index an upstream answers with HTTP
204 adopts.

**Read *Before you upgrade* below first.** Some changes can
surprise a running installation: the package upgrade now restarts a
running daemon, a one-way database migration, an hourly reaper that
deletes idle suites whatever `gc.enabled` says, a new header that
`POST /reconcile` requires, and a stricter signature check that can stop
a suite from adopting.

## Proxy readiness

Suggested by Andy Smith: proxy listeners now provide `GET`/`HEAD /healthz`,
including when admin is disabled. The existing authenticated admin health check
uses the same readiness state. Probes require completed startup, running
listeners, local cache/database checks and usable proxy TLS/MITM certificates;
shutdown or listener failure clears readiness.

Application ports now stay closed through startup preparation. Bind conflicts
are consequently detected after migration, maintenance and certificate setup.
An exclusive `cache.dir/daemon.lock` prevents concurrent daemons on one cache;
stop older versions first, since they do not honor this lock. ACME HTTP-01's
separate challenge port still opens early. See [readiness and load balancers](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/configuration.md#readiness-and-load-balancers)
for the full behavior and HAProxy configuration.

## Usage statistics

The admin dashboard and `GET /?format=json` now report lifetime and since-start
data fetched/served, cache hits, estimated net bytes saved and average effective
download/upload rates. Requested by @sdh91 in issue #11. Totals include background
downloads and retries and persist every 30 seconds and on graceful shutdown,
including with admin disabled. See [usage statistics](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/usage-statistics.md)
for measurement definitions, crash-loss limits and the JSON fields.

## Separate database storage

The optional `[cache] db_dir` setting moves the location of `cache.db` and its
WAL/SHM files independently of cached content, so SQLite can use flash storage
while the pool stays on HDD storage. Empty or omitted keeps the existing layout.
Both the daemon and package commands honor it; health checks also probe a
separate database directory, and the daemon takes a lock in each directory.

To keep an existing cache, stop the daemon and package commands and move the
database files before changing the setting. The directory must already exist
and be writable; the packaged systemd service needs a `ReadWritePaths` override
for locations outside its existing writable root. See
[separate database storage](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/configuration.md#separate-database-storage)
for migration, mount, and Docker setup. When rolling back to a version without
this option, restore the database to `cache.dir` before starting that version.

## Before you upgrade

- **The package upgrade restarts a running daemon.** Upgrading the
  `.deb` to 1.1.0 restarts the daemon if it is running (`try-restart`;
  1.0.x packages left the old binary running until its next start), so
  the migration and the audit below begin as the package is upgraded, and
  the suite reaper an hour later: make the settings below before you
  upgrade. A stopped daemon stays stopped and does all this at its next
  start. After the upgrade, check `systemctl status apt-cacher-ultra` (or
  `journalctl -u apt-cacher-ultra`): apt does not show a new binary that
  exits at startup (the unit is `Type=simple`, so only a restart job that
  fails is reported), and `Restart=always` starts it again every 5
  seconds. See [Upgrading an existing
  cache](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/configuration.md#upgrading-an-existing-cache).
- **The database is migrated one way (schema 6, 7 or 8 to 9), and audited.** At the
  first start the daemon migrates `cache.db` in `cache.db_dir` (or
  `cache.dir` when unset), then audits every
  snapshot an earlier release adopted before it serves anything (INFO
  `legacy_trust_audit_progress` every 100 snapshots; application ports stay
  closed until startup completes). A 1.0.x binary refuses
  the migrated database (`database schema version 9 is newer than this
  binary supports (6); refusing to downgrade`): to keep a way back, stop the
  daemon and copy `cache.db` (and any `cache.db-wal` beside it) before
  upgrading. To go back, stop the daemon first (`systemctl stop
  apt-cacher-ultra`: a refused start runs again every 5 seconds and would
  migrate the copy again, and a copy put back under a running 1.1.0 can be
  undone by its checkpoint), install the 1.0.x package, put the copy back
  as `cache.db` (with its `cache.db-wal` if you copied one, and no other
  `-wal` or `-shm` file beside it), then start it. Go back before
  restarting 1.1.0, and before it has run an hour (or one `gc.interval`,
  if that is shorter). Its first start deletes the snapshots the audit
  quarantined (in its startup GC pass, right after the audit), and the pool
  files only they used go once `gc.blob_grace` has passed since they
  stopped being used — a displaced snapshot's at once, a current one's at
  the next start or GC run; from about an hour after each start (with a
  shorter `gc.interval`, from its first GC run), 1.1.0 also deletes the
  suites it reaps and their snapshots, whose pool files go at its next
  start or GC run (with a shorter `gc.interval`, in that first GC run
  itself). After that, a suite whose current snapshot the audit quarantined
  can answer 502 (`Retry-After: 30`) to its index requests on the restored
  version, until that version adopts the suite again, whenever upstream
  has changed since that snapshot was adopted; every other missing file is
  downloaded again, and nothing is corrupted. The
  audit itself removes only corrupt `InRelease` files; with the
  non-default `hold_packages.window = "0s"`, the first start also drops a
  quarantined suite's packages no client asked for within
  `gc.url_path_ttl`, whose files go at the next start or GC run. The
  daemon refuses to start when the cache's `pool/` directory
  is missing, unreadable or empty — or holds none of the queued inline
  snapshots' files and none of a sample of the files the current
  snapshots use, two or more files checked — while inline snapshots await
  the audit: mount or restore it, or, to start empty, stop the daemon and
  remove `cache.db` (with any `cache.db-wal` and `cache.db-shm`) from
  `cache.db_dir` (or `cache.dir` when unset), and `pool/` from `cache.dir`. Keep `ca/`: unless
  `tls_mitm.ca_storage_dir` is set, it holds the MITM CA the cache
  generated, which your clients trust. The audit then changes nothing, but the database is already
  migrated: going back to 1.0.x needs the copy.
  A snapshot whose stored `InRelease` is not a
  clean signed file, or whose pool file is missing or corrupt, is
  quarantined (WARN `legacy_snapshot_quarantined`): its suite is served
  from the ordinary cache until it adopts again, and a corrupt one's cached
  copies and pool file are deleted, so clients fetch a fresh one. One whose
  pool file cannot be read at all is deferred (ERROR
  `legacy_trust_audit_deferred` at every start) and kept, by snapshot GC
  too, whatever `gc.keep_displaced` is, until the pool is fixed or the
  suite is reaped or forgotten. See [Upgrading an existing
  cache](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/configuration.md#upgrading-an-existing-cache).
- **Offline and archive caches: set `suite_idle_ttl = "0s"` in the `[gc]`
  section before upgrading.** A new suite reaper runs an hour after the
  start and then hourly, whatever `gc.enabled` says, and deletes the suites
  no client has asked for in `gc.suite_idle_ttl` (720 h, 30 days, by
  default), with their cached index files — counted from the last request
  before the upgrade (from 7 days before it for a suite with none, so such
  a suite goes about 23 days after the upgrade). Its first runs also reap,
  however recently used, the rows 1.0.x created for paths this version no
  longer tracks and suites without a snapshot whose cached `InRelease`,
  `Release` and `Release.gpg` are all error pages (INFO `suite_reaped`,
  `reason=non_canonical` or `junk`, up to 250 a run). The reaper deletes
  no package, but a reaped suite's packages lose the version retention its
  snapshot gave them: with GC on and a nonzero `gc.url_path_ttl`, those no
  client asked for within it go after `hold_packages.window`. An install
  that relied on `gc.enabled = false` to keep everything needs the setting
  too. A key in the wrong section is ignored without a warning: within
  the hour after the first start, before the reaper's first run (up to 25
  idle suites and 250 of those rows a run), check that the
  `apt-cacher-ultra starting` line shows `gc_suite_idle_ttl=0s`
  (`"gc_suite_idle_ttl":0` in JSON logs). A reaped
  suite comes back at its next request, fetched from upstream. See [Suite
  reaping](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/configuration.md#suite-reaping).
- **`POST /reconcile` needs the header `X-ACU-Admin: 1`**, as the new
  `POST /forget` does: a script that calls it must add it (403 without). And
  without `admin.htpasswd_file` both refuse (403) a `Host` that is not an IP
  address, `localhost` or the host name in `admin.listen` — a guard against
  DNS rebinding. Behind a reverse proxy that forwards the client's `Host`,
  set `htpasswd_file`, or have the proxy send `Host: 127.0.0.1` only behind
  TLS or in a server block that matches the proxy's own name, never in a
  default or catch-all one (it would pass a rebinding page's requests on
  as if they named the address); in nginx and Apache the only or first
  block on a port is its default, so give the port a default block that
  refuses other names (nginx: `listen 80 default_server; return 444;`). A
  browser
  request from another origin is refused too. Its other answers: 400 (was
  413) for a body that is not a form, 400 (was 409) for a `scheme` other
  than `http` or `https` and for a `host` holding `://`, 409 also when no
  adoption slot is free, 413 for a body over 8 KiB; every error body ends
  in one newline (it was two), and `OPTIONS /reconcile` names
  `Allow: POST, OPTIONS`. See [the admin
  listener](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/configuration.md#admin-status-metrics-and-maintenance).
- **`adoption.require_signature = false` no longer adopts unsigned
  metadata.** It only lets the daemon start with an empty keyring; the
  inline form is adopted only from a decodable clearsigned `InRelease`, in
  every mode. Unsigned repositories are adopted by
  `adoption.adopt_unsigned` (default `true`) instead, as unsigned snapshots
  that vouch for no package. This affects only a deployment whose
  `InRelease` URL serves a body that is not clearsigned — which apt itself
  rejects on its first line. The startup WARN that names the setting is now
  `adoption_require_signature_disabled`.
- **A database error creating a suite's row now fails the request.** The
  row is created in the same transaction as the file's cached copy, so such
  an error is a 502 with ERROR `unclassified fetch error` (`err`
  `handler: put url row: …`), where 1.0.x served the file and logged WARN
  `seed suite_freshness failed`. A refusal at the new `freshness.max_suites`
  caps is no error: WARN `suite_seed_rejected`, and the file is still served
  and cached.
- **Strict mode now covers flat repositories.** With
  `integrity.refuse_unvouched_debs = true` (and adoption enabled), a host
  that serves only flat repositories becomes strict as soon as one of them
  has a signed snapshot, as long as every signed snapshot on the host has
  complete coverage. A `.deb` there that no signed snapshot vouches for is
  then refused (502) where 1.0.x passed it through: a file the vendor
  serves beside a repository without listing it, every package of an
  unsigned or Release-less repository on that host, and — right after the
  upgrade — the packages of the host's flat repositories that have not
  adopted yet. A host adopts one suite at a time, so its repositories
  adopt one after another, usually within a few minutes, each one's
  packages refused until its own adoption; later, the first install from a
  newly added flat repository is refused while its first adoption waits
  for a slot. A signed flat snapshot with incomplete coverage turns strict
  mode off for its whole host, as a `dists/` one does. See [strict
  mode](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/configuration.md#integrity-corruption-checks).
- **Caches in front of a very large host: raise `freshness.max_suites`
  first.** The cache now tracks at most `freshness.max_suites` suites
  (5000 by default) and a tenth of that per upstream host. A cache that
  already holds more keeps them and logs WARN `suite_caps_exceeded` at
  start, but a host at its cap gets no new suite: its new repositories are
  served as first cached and never refreshed or adopted (WARN
  `suite_seed_rejected`) until idle suites are reaped. Above the total
  cap no host gets one: each refused new suite evicts one suite that has
  no snapshot and that no client asked for in 24 hours, so on a cache
  with adoption enabled, where few suites qualify, the refusals can last
  until the reaper deletes idle suites. Raise the key
  before upgrading a cache that fronts an Artifactory, aptly or Nexus host
  with hundreds of suites. See [Tracked
  suites](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/configuration.md#tracked-suites).
- **First adoptions after the upgrade.** With adoption enabled, each tracked
  suite without a snapshot that a client asked for in the 7 days before the
  upgrade, or asks for later, is adopted at its first check — one at a time
  with the default `freshness.max_concurrent_adoptions = 2`, while signed
  updates keep a slot of their own; `3` runs two at once. Snapshots adopted
  before the upgrade carry no SHA512 by-hash names: such requests get 404
  from the snapshot, and apt then fetches the file by name, until the
  suite's next adoption. 1.0.x never adopted a flat repository; 1.1.0
  adopts every one your clients use, so first load their signing keys on
  the cache host (`/etc/apt/keyrings` or `adoption.keyring_dirs`; the
  daemon reads keys only at startup; with `adoption.accept_any_signer =
  true` a host no `[[trusted_signer]]` rule names needs none), and with
  `adoption.require_pinned_signer = true` their `[[trusted_signer]]`
  rules: otherwise each one's adoption fails (outcome `gpg_failed` or
  `unpinned_suite`, the latter with WARN `adoption_unpinned_suite`; WARN
  `adoption_run_failed` at every retry, up to hourly, and
  `adoption_failing_persistently`), it stays as stale as on
  1.0.x, and in strict mode its packages are refused once another
  repository on its host has adopted.
- **The signature check is stricter, and a refusal stops a suite's
  adoptions.** An anchor whose format some supported apt refuses — a line
  after the signature, a forged armor checksum, damaged armor, bytes
  around a `Release.gpg`'s armor or a binary one — or that lies outside
  the shape real signers write (a second armor block, a signature packet
  the cache cannot parse, a version 3 signature such as pkgs.k8s.io
  v1.30's) is refused as `malformed_clearsign` (an `InRelease`) or the new
  `malformed_signature` (a `Release.gpg`); a bad signature from any key
  the cache holds beside a good one, whatever that key's usage, as
  `bad_signature`; and an anchor whose only good signature is SHA-1 as
  `crypto_verify_failed`. The suite keeps serving its current snapshot and
  stops adopting until upstream publishes an anchor the cache accepts;
  INFO `adoption_gpg_failed` names the rule or the key. A snapshot 1.0.x
  adopted keeps serving whatever the new rules make of its anchor (the
  trust audit does not run the verifier): it is the suite's next adoption
  the rules decide. Key files are read as the apt clients read them
  (every armor block, the keys before junk at a file's end, files up to
  256 MiB); a revocation or expiry the cache cannot read stops that key
  from counting (INFO `keyring_key_marked` at start), and a skipped or
  truncated file logs WARN `keyring_file_skipped` or
  `keyring_file_truncated`. Install in the cache every key your clients'
  `signed-by` names, so that it refuses what they would. On the first
  start, read the first hour's `adoption_gpg_failed` lines and compare
  each with what your clients' apt does on that repository. See [Trust and
  signer pins](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/configuration.md#trust-and-signer-pins).
- **The signer downgrade guard refuses an anchor that lost its strong
  signer.** A *strong* signer is a key `debian:13`, `ubuntu:24.04` and
  `ubuntu:26.04` all accept (Ed25519, ECDSA P-256 or P-384, RSA of 3072
  bits or more, or of 2048 to 3071 bits until 2030-02-01, bound with
  SHA-256 or better). When a suite's current
  anchor has one and a new anchor has none — the shape of an on-path strip
  of a strong signature beside a weak one — the new anchor is refused
  (refusal `signer_downgrade`, WARN `adoption_signer_downgrade`, counted
  by `acu_adoption_refused_total{reason}`) and the current snapshot keeps
  serving, its lag showing. A vendor that rotates to a new strong key the
  keyring does not hold yet is refused too: install the new key, once
  confirmed out of band (the vendor's announcement, site or key-rotation
  notice), and restart; the suite adopts at its refusal's next retry, at
  most 75 minutes later. Otherwise confirm with the vendor that it really
  dropped its strong signer before `POST /forget` or removing the old key,
  since both adopt the anchor the guard refused. The guard cannot see a
  strip at a suite's first adoption. Six surveyed vendors sign with no
  strong key (ceph, mongodb, newrelic, nvidia-cuda, openresty and
  raspberrypi): `debian:13` clients refuse their anchors with or without
  the cache, and the guard stands down for their suites. See [Trust and
  signer pins](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/configuration.md#trust-and-signer-pins).
- **Smaller behaviour changes.** Upstream request lines with `+` or `~` in
  the path are now encoded exactly as apt encodes them. A few `dists/`
  paths apt never sends no longer get a suite: they are served but not
  tracked. A repository that publishes only `Release` and `Release.gpg`
  (pkg.jenkins.io) and that the cache first sees after the upgrade is not
  tracked while adoption is disabled; one 1.0.x already tracked stays
  tracked. A plain-text `InRelease` (no clearsign line, which apt rejects
  too) no longer tracks a suite. In strict mode, a `.deb` miss whose
  vouching hashes could not be read before its download (new WARN
  `package_hash_prefetch_lookup_failed`), or that was vouched then but no
  longer is once downloaded (its snapshot retired, or replaced by one that
  no longer lists it, meanwhile), is checked after it, and refused then if
  strict mode refuses it; 1.0.x served it, logging nothing above DEBUG.
- **Alerts on log lines change at the restart.** Six 1.0.x messages are
  gone, and four new events begin with `freshness_check`, so a substring
  match on it now matches them too: adjust such alerts before upgrading
  (*Removed messages* and *Matching an event exactly*, under *Logging and
  metrics* below).
- **New configuration keys**, each with the default shown; the packaged
  `config.toml` lists them with comments, and a key left out of yours takes
  its default. An edited `config.toml` is a conffile: dpkg asks at the
  upgrade whether to keep it, and keeping it (the default) puts the
  packaged one beside it as `config.toml.dpkg-dist`:

  | Key | Default | Rule |
  |---|---|---|
  | `adoption.adopt_unsigned` | `true` | adopt repositories that publish an unsigned `Release` |
  | `adoption.flip_quiet_period` | `"10s"` | `0s` disables the flip barrier; otherwise `1s` to `15s` |
  | `adoption.max_duration` | `"30m"` | at least `1m` |
  | `freshness.max_suites` | `5000` | at least 10; a tenth of it per upstream host |
  | `gc.suite_idle_ttl` | `"720h"` | `0s` disables suite reaping; otherwise at least `24h` |

## What's new

- **Flat repositories** are tracked, refreshed and adopted like `dists/`
  ones, in both source forms (`deb <uri>/ /` and `deb <uri> ./`, two suites
  that share their signing history) and with a subdirectory
  (`deb <uri> binary/`); their packages are vouched by the paths apt
  requests, including `./…` Filenames and Filenames above the `Release`
  (pkg.jenkins.io, Sublime Text). A flat repository at the root of its host
  is not supported (WARN `flat_host_root_unsupported`). See [Flat
  repositories](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/configuration.md#flat-repositories).
- **Unsigned repositories** are adopted as unsigned snapshots — served
  coherently, never trusted, never vouching — after two checks see the same
  `Release` at least 5 minutes apart (with the default `cooldown` and
  `periodic_refresh`, usually 5 to 15 minutes after the first
  `apt update`; at least an hour when its host answers 401 or 403 for the
  missing signature file, as Amazon S3 does), and never once the cache
  has seen the repository signed. **Release-less flat repositories**
  (Gemfury, goreleaser) are refreshed file by file. **SHA512-only
  `Release` files** adopt, and by-hash requests are answered for SHA256
  and SHA512. Read the [threat
  notes](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/configuration.md#anchor-forms-and-unsigned-repositories) before
  serving unsigned repositories; `adoption.adopt_unsigned = false` turns
  them off.
- **Outages that answer with HTML** — a captive portal, a vendor's
  maintenance page — never replace a Release-less repository's cached
  index. The pages a client's own update cached during the outage as the
  repository's `InRelease` and `Release` are deleted by the first check
  after it, so the next update is clean; one cached as its `Release.gpg`
  stays, harmless while the repository publishes no `Release`, and is never
  served once the repository adopts one. See [Flat
  repositories](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/configuration.md#flat-repositories).
- **Eager first adoption:** a new repository is adopted at its first
  `apt update` through the cache, when an adoption slot is free, in
  whichever form its upstream publishes; a suite nobody asked for in 7 days
  costs no upstream request. See [Eager first
  adoption](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/configuration.md#eager-first-adoption).
- **Retry discipline:** a failed adoption is retried after 2 minutes,
  doubling to an hour (±25 %), instead of at every check, and new upstream
  content is tried at once; eight outcomes are refusals — states the status
  page shows as "refused: …" — not failures. Checks run on four workers with
  per-host fairness and their own backoff. See [How failed adoptions are
  retried](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/configuration.md#how-failed-adoptions-are-retried) and
  [Capacity and fairness](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/configuration.md#capacity-and-fairness).
- **Flip consistency:** a new snapshot waits until clients that received
  the old `InRelease` have had `adoption.flip_quiet_period` to fetch its
  indexes, holding new `InRelease`/`Release` requests at most 20 s (below
  apt's 30 s timeout), and by-hash requests are served from displaced
  snapshots. See [Flip
  consistency](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/configuration.md#flip-consistency).
- **Suite lifecycle:** the hourly suite reaper (above) and `POST /forget`,
  which reaps one suite at once — the way out of a deliberate upstream
  rollback and of a vendor that stopped signing or dropped its strong
  signer (`signer_downgrade`: confirm with the vendor first; see the
  guard above). See [Forgetting a
  suite](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/configuration.md#forgetting-a-suite-post-forget).
- **Strict mode waits** up to 15 seconds for a signed adoption running on
  the request's host before it refuses a `.deb`, so a package from an
  update being adopted is served.
- **The status page and JSON** gain (additive): `suites[]`'s `scheme`,
  `flat`, `anchorless`, `anchor_form`, `last_requested_unixtime`,
  `check_fail_count`, `adoption_fail_reason`, `adoption_fail_count`,
  `adoption_fail_first_unixtime`, `adoption_next_retry_unixtime` and
  `adoption_refused`; `recent_adoptions[].scheme`; `gc.retired_reaped`; and
  on the page a *Last requested* column, failures and refusals in the
  Adoption cell (`checks failing ×k · backoff ends in …`, `refreshed without
  a Release`), and `scheme://host` cells.
- **The signature verifier** reads an anchor as apt does: apt's own text
  layer ported, a canonical armor and packet grammar real signers write,
  then each signature checked alone; a crafted signature packet can no
  longer make the daemon allocate gigabytes and be killed. Format rules
  hold over every supported client generation (an older client's refusal
  counts for a shape no real signer writes), crypto policy follows the
  gpgv-based apt, and only the signer downgrade guard judges key
  strength. See [Trust and signer
  pins](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/configuration.md#trust-and-signer-pins).
- **HTTP 204:** an empty repository index an upstream answers with 204
  (GitLab's Debian registry does) adopts, and a client's request for such
  an index or metadata file is served as an empty file; a 204 for an
  `InRelease`, `Release` or `Release.gpg`, or for a package file, stays an
  upstream error (502, nothing cached). A 204 logs `upstream_status` 204
  and counts in `acu_fetch_total{outcome="no_content"}`.
- **Garbage collection on a busy cache** (issue #14): a pass that runs out
  of `gc.max_tick_duration` no longer ends the run, so the pass that
  deletes unused files is no longer skipped behind the others, and retired
  snapshots left over are deleted hourly until none is left, and at every
  start. A run that ends with `deadline_reached=true` is now normal while a
  backlog drains: the status page shows it as WATCHING, no longer
  DEGRADED. A pass also gives up a database write it cannot start before
  its deadline, so a busy writer no longer pushes GC past its
  `gc.max_tick_duration`. The startup pass now retires the displaced
  snapshots beyond `gc.keep_displaced` and deletes them in 10,000-row
  transactions, as a periodic run does, instead of deleting them in one
  transaction, so a start's `displaced_reaped` counts them again in
  `retired_reaped`.
- **Displaced snapshots' package lists** (issue #14): GC now deletes a
  displaced snapshot's package list (its `package_hash` rows, 70,000 to
  100,000 for a large suite) soon after it is displaced, 10,000 rows a
  transaction, in the startup pass, the periodic runs and the hourly
  retired runs, so the table shrinks to roughly the current snapshots'
  size. `gc.keep_displaced` now keeps displaced snapshots' headers and
  index files (inspection, the rollback check and by-hash serving use
  those), not their package lists. The first start after the upgrade
  strips the existing backlog within its GC budget; the hourly runs take
  the rest. The database file does not shrink: SQLite reuses the freed
  pages. To return the space to the filesystem, run `VACUUM` on the
  database while the daemon is stopped; it is optional. A GC sub-job that
  fails no longer stops the ones after it: each logs its own
  `gc_tick_failed`.
- **Robustness:** an `InRelease` the signature library cannot decode no
  longer crashes the daemon; a backward clock step no longer freezes
  freshness checks; panics in freshness checks, adoptions, the reaper and
  GC — its startup pass included — are recovered and logged; idle SQLite
  read connections are kept between requests (fewer connection churns
  starving the writer).
- **Built with Go 1.27**; source builds require Go 1.26 or newer. Dependency
  updates include Lego v5.6.0 and maintained cryptographic libraries; exact
  versions are recorded in [go.mod](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/go.mod). Reachable dependency
  vulnerabilities are checked in CI without suppressions.

## Server HTTPS and automatic certificates

Admin and cache TLS listeners can use existing PEM certificate/key files or one
shared ACME certificate. File certificates reload every minute without a restart;
an invalid replacement retains the previous valid certificate. Built-in ACME
supports HTTP-01 and DNS-01 through Lego's full automated provider catalogue,
with private account/certificate storage, restart-safe retry deadlines, renewal,
and certificate status/metrics. A valid saved certificate permits offline startup.

These features are opt-in. Admin authentication remains necessary, and the
repository MITM CA is configured independently. DNS-01 requires provider
credentials in environment variables or supported credential files and needs no
inbound challenge port. One DNS name is supported; wildcard/multi-name
certificates and external account binding are not included.

Follow [server HTTPS setup](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/server-tls.md) for configuration, staging,
credential permissions, Certbot integration, backup/recovery, and Docker
healthchecks that verify certificates. The packaged systemd service now allows
six minutes for shutdown so DNS record cleanup can finish after application
listeners stop. The full provider catalogue increases executable size and build
memory requirements; the guide also covers optional smaller custom builds.

## Logging and metrics

Optional `cache.trusted_proxies` enables `X-Forwarded-For` client-address
logging behind explicitly trusted proxy IPs/CIDRs. The default empty list
preserves existing behavior. When a forwarded address is accepted,
`client_addr` is an IP without a port and the new `peer_addr` field retains
the proxy's socket address. Chains are checked right to left; CONNECT inner
requests inherit the outer identity. See [setup and trust requirements](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/configuration.md#logging-client-addresses-behind-a-proxy).

Every new log message is a snake_case event name, and a test keeps it so;
the prose messages 1.0.x logs are unchanged but for the six below. Every
event this release adds is documented in [the log field
reference](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/log-fields.md).

### Removed messages

An alert that matches one of these stops firing on upgrade:

| 1.0.x message | Level | 1.1.0 instead |
|---|---|---|
| `adoption.require_signature = false: unsigned upstream metadata would be adopted (auditable per SPEC2 §5.1)` | WARN | WARN `adoption_require_signature_disabled` — and a behaviour change: see *Before you upgrade* |
| `freshness: no baseline blob hash, skipping` | DEBUG | DEBUG `freshness_check_skipped_no_baseline_anchor_hash` (`anchor` is `InRelease` or `Release`) |
| `freshness: no baseline Release blob hash, skipping` | DEBUG | the same event |
| `freshness: unexpected success status` (`status`) | ERROR | INFO `freshness check failed` with `err` `unexpected success status <code>` and `result=failed`, counted in `acu_freshness_check_total{result="failed"}`: match the `err` text, not the level |
| `freshness: persist anomaly failed` | WARN | WARN `freshness: persist failure-bump failed`: the anomaly now goes through the failed-check bookkeeping |
| `seed suite_freshness failed` | WARN | no line of its own: a 502 and ERROR `unclassified fetch error` (see *Before you upgrade*) |

One changed text an alert may match: `source_parse_failed`'s `error`
field said `sources: no stanzas with Package + Directory +
Checksums-Sha256`; it now says `sources: every path refused by
validateMemberPath (N skipped)` or `sources: no stanza with Package,
Directory and a well-formed Checksums-Sha256 entry`.

### Matching an event exactly

On 1.0.x `freshness_check` was the only event with that prefix; 1.1.0 adds
`freshness_check_cancelled`, `freshness_check_ended_by_shutdown`,
`freshness_check_skipped_no_baseline_anchor_hash` (DEBUG) and
`freshness_check_panicked` (ERROR), so a substring query such as
`|= "freshness_check"` matches them too, and so does `msg=freshness_check`.
Match the name exactly: in JSON logs `"msg":"freshness_check"` with its
closing quote; in text logs, where the name is written unquoted,
`msg=freshness_check` followed by a space or the end of the line (the regex
`msg=freshness_check( |$)`); or a parsed field, such as LogQL's
`| json | msg="freshness_check"` or `| logfmt | msg="freshness_check"`.

Two WARNs 1.0.x already logs repeat at every adoption with nothing for the
operator to do: `source_parse_failed` for a `Sources` file whose every path

member your own `adoption.architectures` filters out. If you page on every

- The `request` line: `snapshot_displaced` (a by-hash request served from

### Alerts worth adding

- **The suite reaper stopped:** `absent(acu_suite_reaper_last_run_unixtime)`
  held by a Prometheus `for: 3h`, or
  `time() - acu_suite_reaper_last_run_unixtime > 3 * 3600`. A restart or
  one failed run never pages; a reaper that stopped completing runs pages
  within about three hours.
- **GC:** ERROR `gc_panicked`, and
  `time() - max(acu_gc_last_run_unixtime) > 2 * 86400 + 3600` with the
  default 24 h `gc.interval` (two intervals and an hour): a panic in GC no
  longer stops the daemon, at startup or in a tick, so the gauge's age is
  what shows GC stopped completing; one failed tick never pages.
- **Flips slower than their hold:** `rate(acu_flip_hold_expired_total[1h]) > 0`
  (a commit slower than 20 s; see [Flip
  consistency](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/docs/configuration.md#flip-consistency)).
- The `…_panicked` ERRORs above, and `acu_freshness_unlogged_panics_total`
  or `acu_flip_gate_panics_total` above 0: each is a bug; please report
  it. `legacy_trust_audit_deferred` and `legacy_anchor_discard_failed` are
  disk faults in the cache directory.

## Testing

- **`make e2e-flat`** is new: real apt clients — apt 2.2 to 3.2, on six
  Debian and Ubuntu images — against fixtures of every supported repository
  layout through the cache, about 25 minutes in sequence; CI runs one job
  per image. Fixtures only: it never reaches a live repository. `e2e/deb`,
  the package-install check, was updated for eager first adoption, and now
  checks the maintainer scripts against a stub `systemctl`: a fresh
  install (the install message, no restart), the upgrade of an enabled
  unit (one `try-restart`, no stop, no install message), a failed restart
  (dpkg still succeeds), `policy-rc.d`'s refusal honoured, `abort-upgrade`
  (one `try-restart`) and a plain `abort-remove` (none), neither with the
  install message, the removal (stop and disable), a reinstall after it
  (the install message), and no systemd or `DPKG_ROOT` set (no
  `systemctl` call, the install message).
- **`make e2e-live`** is the manual smoke against live flat repositories,
  run before 1.1.0 and before later releases that change the request path,
  adoption or vouching. On 2026-10-28, on the final tree, with adoption
  and strict mode on:
  - pkgs.k8s.io v1.36 and v1.37, each in both source forms (four suites):
    adopted inline; `kubectl` 1.37.1 and 1.36.5 installed, vouched.
  - NVIDIA CUDA (debian12/x86_64; 9,768 packages): adopted inline;
    `cuda-toolkit-12-config-common` installed, vouched (`./…` Filenames).
  - libnvidia-container (a SHA512-only `Release` dated 2018): adopted
    inline; `nvidia-container-toolkit-base` installed, vouched.
  - pkg.jenkins.io (`binary/`, `Release` and `Release.gpg` only): adopted
    detached; `jenkins` 2.580.1 installed, vouched (Filenames one level
    above the `Release`).
  - download.sublimetext.com (`apt/stable/`): adopted inline;
    `sublime-merge` 2132 installed, vouched (Filenames at the host root).

  Every `apt-get update` was clean (and both of the error grep's controls
  were caught), strict mode refused an undeclared `.deb` on each of the
  five hosts, and nothing else was refused.
- **`make e2e-apt-oracle`** and **`make e2e-apt-oracle-old`** are new and
  manual, run before every release: the real apt of six current client
  images, and of five older ones (Debian 10, Ubuntu 20.04, 18.04, 16.04
  and 14.04), must still give the verdicts and error classes recorded for
  the verifier's 904 signature-shape fixtures, which the verifier's own
  table test holds the cache to in CI. See
  [e2e/apt-oracle/README.md](https://github.com/linsomniac/apt-cacher-ultra/blob/1.1.0/e2e/apt-oracle/README.md).
- Release binaries never contain the end-to-end tests' seam: CI and the
  release workflow refuse a binary built with `-tags e2ehooks`.
